# Danygramm: проверка выделения голоса владельца

Дата: 20 октября 2026. Задача: `miccontrol-adn`; диагностический native-прототип: `miccontrol-ulk`; ошибка выбора говорящего: `miccontrol-m1b`.

## Решение по включению в приложение

**VoxLock в проверенной конфигурации пока не подходит для выпуска режима «только мой голос».** На части независимых записей он пропускает постороннего говорящего, а при наложении голосов иногда выделяет постороннего вместо владельца. Ошибка воспроизводится и в исходном Python, и с полной FP32-моделью. Это недостаток проверенной модели, а не исправление, которое можно сделать увеличением шумоподавления.

Подготовлен отдельный C++-прототип и инструменты измерения. Они не подключены к CMake/Gradle приложения, не меняют настройки пользователя и не входят в APK 1.0. Модели, записи и бинарные библиотеки не добавляются в Git.

## Что именно проверялось

- [VoxLock](https://github.com/arbazsiddiqui/voxlock), исходники `08ed37cbb79f449ca6b499bc23fb14138b207bfd`.
- [Веса](https://huggingface.co/arbazsiddiqui/voxlock), revision `a50f4e1d109301d4b6f61dec57ebb1a61e7d8f03`.
- CPU ONNX Runtime 1.31.0, spinning выключен. Для исходного сравнения — четыре потока, моно 16 кГц, блоки по 640 отсчётов (40 мс).
- Независимые фразы трёх мужчин из официального [LibriSpeech test-clean](https://www.openslr.org/12): A — 6930, B — 1320, C — 5639. По три разных файла на человека. Для регистрации и проверяемого голоса используются разные фразы.
- Исходная смесь: A; B; A+B; A+2B; B после наложения; тишина. Каждый сегмент имеет 53 040 отсчётов, вся запись — 318 240. Для C++ golden-теста запись дополнена нулями до 318 720, кратно 640.
- Дополнительная матрица: девять образцов регистрации × три независимых чистых запроса (27 случаев), затем три пары говорящих × три профиля (9 случаев). Тишина не считается доказательством сохранения речи.

## Результаты качества

На исходной длинной смеси при правильном выборе A/B полная int8-квантизация дала улучшение SI-SDR на участке равного наложения **10,64 / 17,23 дБ**. Это подтверждает настоящее разделение говорящих, но не универсальную надёжность выбора владельца.

На чистом запросе правильного владельца все девять вариантов регистрации сохраняли речь: изменение RMS от +0,21 до +0,67 дБ. Среди 18 запросов без владельца четыре имели подавление слабее 20 дБ; этот порог используется только для описания диагностики, а не как подтверждённый критерий качества продукта.

Критический контрпример: профиль C из `5639-40744-0032.flac`, запрос B из `1320-122617-0012.flac`. C отсутствует, но B проходит с gain **1,077** и изменением RMS **+0,65 дБ**. Разные SHA-256 записей и разные признаки регистрации исключают случайное повторное использование одного образца.

На смеси B+C с тем же профилем C результат преимущественно содержит B. Коэффициенты линейной проекции выхода на известные исходники:

| Точность модели | Чужой B | Нужный C |
| --- | ---: | ---: |
| int8-full | 0,92866 | 0,11174 |
| FP32 | 0,92826 | 0,11197 |

Полная FP32-точность воспроизводит ошибку. Замена образца C на другую независимую фразу меняет результат, но сама по себе не даёт гарантии. Отдельная проверка говорящего может отвергнуть неверный выход; восстановить уже потерянный голос владельца она не может.

Независимая проверка WeSpeaker с подготовкой признаков по официальному reference (Kaldi Hamming, полные окна, utterance CMN) отличает ошибочно выделенного B: например, B-only выход имеет cosine **0,07696** с C и **0,64467** с B. Все шесть независимых трёхсекундных фраз распознаны правильно. Первоначальный маршрут через metadata/defaults SDK не соответствовал reference; его плохой результат не считается доказательством непригодности speaker verification.

Более короткие окна проверены отдельно: 72 × 250 мс, 36 × 500 мс и 18 × 1 с. На 250/500 мс genuine/impostor оценки пересекаются; на 1 с получены 18/18 правильных выборов только на этом малом наборе. Надёжный допуск не выбран. Буферизация секундного решения добавляла бы секунду задержки до отправки аудио, а без неё уже отправленную чужую речь нельзя отозвать. [Методика, preprocessing и все результаты](../../code-reviews/2026-10/CR-2026-10-20-speaker-verification-diagnostic.md).

## Android: реальный native CPU-прогон

Standalone PIE собран NDK 27.2.12479018 / API 24 с C++17, `-Werror`, static libc++ и LOAD alignment 16 КиБ. Используется только native C API официального ORT AAR; Java telemetry provider не добавляется. SHA-256 AAR `72683787a80d0608a3121b967d8e1239aef48286826661c953211626690540a7`, arm64 SO `8005a741e57117b4d7b476417706c0e9af13cf1b89db47e60f0cbc56e1af91e0`.

Среда: arm64 эмулятор API 36, фактический размер страницы 16384; четыре CPU. Во время трёх основных прогонов остальные модельные вычисления на хосте остановлены. Это **не замер на vivo X200 Ultra** и не доказательство скорости/энергопотребления на физическом телефоне.

| Профиль | RTF | P95 блока, мс | P99, мс | Пиковый RSS, КиБ |
| --- | ---: | ---: | ---: | ---: |
| A / 6930 | 3,429745 | 153,606864 | 209,932723 | 192512 |
| B / 1320 | 3,366102 | 162,827898 | 202,872626 | 191728 |
| C / 5639 | 3,634275 | 157,589139 | 237,459002 | 192096 |

RTF = время Push+Flush / длительность звука, без загрузки и регистрации. Для непрерывной обработки нужен RTF ниже 1 с запасом. Проверенная четырёхпоточная конфигурация этот критерий не проходит; большие очереди лишь накапливали бы задержку звонка.

Все три прогона сохранили количество отсчётов, форму тензоров и конечные числовые значения. Android-выход близок к Python, но не совпадает точно: RMS ошибки A/B/C — 0,0009982 / 0,0007756 / 0,0006467, cosine — 0,9997966 / 0,9999319 / 0,9999553. Строгая побитовая идентичность Android не заявляется. Анализ переноса и проверка на Mac отделяют математику C++-обёртки от численного пути ORT на другой платформе.

Контроль гипотезы о числе потоков: финальный native-прототип с дополнительной проверкой конечности overlap-add пересобран отдельно и запущен на первых четырёх секундах входа. Один поток: RTF **3,808883**, P95 **174,526906 мс**; два потока: RTF **3,304806**, P95 **155,843942 мс**. Выход конечен, длина 64 000 сохранена; сравнение конца с полной длинной записью намеренно не выполняется из-за другого reflect-flush. Обе конфигурации медленнее реального времени, поэтому перебор настроек остановлен. В CPU metadata эмулятора есть `asimddp`; отсутствие этого флага не объясняет результат.

## Проверенные изменения экспериментального графа

Регистрация шести секунд сначала выявила ошибку экспорта: metadata объявляет динамическую длину `context`, но 64 shape-константы внутри 32 attention-блоков фиксируют 298 кадров, соответствующие трём секундам. [Guarded helper](../../../../tests/miccontrol/repair_voxlock_context.py) заменяет только эти константы на фактическую длину. SHA-256 всех 685 initializer и 7409 остальных узлов сохранены; ONNX checker прошёл. Оба полных трёхсекундных golden A/C по-прежнему побитово совпадают.

Четыре шестисекундных теста после исправления выполняются. Непрерывный образец C почти не исправляет выбор B; объединение двух разных трёхсекундных фраз улучшает смесь: gain B/C становится **0,39969 / 0,58313** вместо **0,92866 / 0,11174**. Однако в B-only запросе обе шестисекундные регистрации сохраняют чужую речь с gain около **1,077**. Более длинная регистрация не прошла критерий отсутствующего владельца.

Отдельная оптимизация заранее вычисляет постоянные признаки публичного профиля A/C: 32 повторяемых узла MatMulIntegerToFloat удалены, оптимизированный граф сократился с 3213 до 3142 узлов. C++ не менялся. Полные A/C результаты и recurrent state совпадают с исходными; ошибочный C→B тоже сохраняется. Для Android использована переносимая копия графа, без оптимизаций под ISA Mac.

На том же четырёхсекундном Android-входе и двух потоках RTF улучшился с **3,304806 до 2,874009** (примерно 13%), P95 — **131,707973 мс**, RSS — **205904 КиБ**. Сравнение с исходным Android-выходом: cosine **0,9999953**, RMS ошибки **0,0001803**, отношение энергии **0,9998671**. Это улучшение всё ещё недостаточно для real-time на эмуляторе.

[Freeze helper](../../../../tests/miccontrol/freeze_target_voice_context.py) жёстко ограничен публичными тестовыми профилями. Его пяти-входная compatibility-копия намеренно игнорирует переданные признаки и всегда выбирает A. Она нужна только для этого измерения и **не может поставляться как приложение или применяться к другому владельцу**. Веса и производные графы остаются вне Git.

## Проверка корректности C++ отдельно от качества модели

На Mac arm64 с тем же CPU ORT 1.31.0 все три C++-выхода **побитово совпали** с независимым Python Stream: по 318 720 отсчётов, максимальная и RMS ошибки равны нулю. Основной агент дополнительно сравнил сами файлы побайтно. Это локализует Android-различие в численном пути другой платформы, а ошибку выбора C→B — в модели: она уже присутствует в Python и FP32.

ASan + UBSan прошли на полной записи с проверкой Reset из активного и завершённого состояния, времени жизни модели/профиля, некорректных входов и Flush. LeakSanitizer на этом macOS target не поддерживается; отдельный системный `leaks --atExit` на коротком реальном прогоне с Reset сообщил **0 утечек / 0 байт**. Это не проверка всех выделений внутри неинструментированной ORT-библиотеки. [Подробный review прототипа](../../code-reviews/2026-10/CR-2026-10-20-target-voice-native-prototype.md).

## Артефакты и дальнейший критерий приёмки

Локальные данные в игнорируемом `artifacts/qa/target-voice/`:

- `speech/source.json` и девять официальных FLAC; `host-benchmark.json`, `absence-matrix.json`, `precision-control.json`.
- `golden/manifest.json`: точные raw little-endian Float32 входы, Python-выходы и SHA-256.
- `android/result.json`, `android/probe-*.json`: native-показатели, проверенные входы и численные различия.
- `android-thread-probe/result.json`: отдельная проверка одного/двух потоков на финальном C++.
- `native-macos/verification.json`: SHA-256 исходников, точное совпадение трёх выходов, sanitizers и системная проверка утечек.
- `dynamic-context/quality6s.json`: исходные и исправленные shape-контракты, точное совпадение 3s и результаты 6s.
- `frozen-context-canonical/host-proof.json`, `android-frozen-context/result.json`: проверка выноса неизменных вычислений и реальный native-замер.

Команды воспроизведения: [TARGET_VOICE_TESTS.md](../../../../tests/miccontrol/TARGET_VOICE_TESTS.md). Генератор проверяет SHA-256 исходников модели, всех девяти FLAC и весов; runtime-бинарники также привязаны к точным SHA-256. Он не скачивает и не запускает случайную новую версию модели.

Для включения в приложение нужны: исправленный выбор владельца на независимых голосах и отсутствующем владельце; сохранение речи при наложении и более громком собеседнике; проверка коротких реплик, каналов/языков и шума; достаточная скорость и ограниченная очередь; безопасные запись/отмена/удаление профиля. Отдельно необходима физическая проверка телефона и Bluetooth, а не повтор старых тестов авторизации.

Проект интерфейса и жизненного цикла описан в [target-voice-enrollment-design.md](target-voice-enrollment-design.md). Текущие профили VoxLock содержат около 1 МБ производных акустических данных и могут сохранять восстанавливаемую речь: это не необратимый маленький идентификатор. Лицензии моделей, их компонентов и наборов данных должны сохраняться при любом будущем распространении.
